## Best-supported cause
The strongest explanation is **slow or unanswered EU-1 authorizations, amplified by v2.14.0’s longer timeout and more permissive retry policy**. The provider’s reported impact window overlaps the checkout slowdown, and traces directly show checkout time spent waiting on payment attempts rather than database or other checkout steps. [provider-status:L7-L9] [traces-2026-10-06:L331-L338] The release did not necessarily cause the gateway fault; its payment-client settings made requests wait longer when the gateway failed to respond. The payment log also records 8-second timeouts and retries during the slowdown. [payment-client-log:L184-L191]

## Competing explanation
The main competing explanation is the orders-db CPU warning and concurrent reindex. That work did raise CPU from roughly 30–38% to 80–92%, so it was a real concurrent load event. [db-metrics:L122-L140] However, database query p95 stayed around 24–30 ms during the slowdown, while sampled checkout traces show database operations taking only 16–30 ms and payment authorization taking over 8.5 seconds. [db-metrics:L132-L162] [traces-2026-10-06:L331-L338] Further, database CPU returned to normal at 14:41 while checkout latency remained high. [db-metrics:L162-L168] [checkout-metrics:L163-L175] The database event is therefore a weaker explanation for the checkout latency than the payment path.

## Recommended mitigation
With incident-commander approval, **revert only the checkout-api payment-client runtime profile from v18 to v17** using the documented config rollback. The runbook says this change propagates within about 60 seconds and is reversible by rolling forward. [runbook-payments:L14] This is narrower than redeploying the previous release and avoids touching database state. It restores the prior payment-client behavior indicated by the diff: shorter timeout and fewer retries. [config-diff:L35-L43] Preserve fraud screening and idempotency behavior; do not open the circuit breaker unless there is a full gateway outage. [runbook-payments:L5-L8] [runbook-payments:L16]

## Uncertainty
The evidence supports a combined gateway-degradation and client-policy explanation, but does not isolate how much of the latency increase came from the gateway fault versus the changed timeout/retry policy. The traces are sampled, and the per-minute metrics do not show every request. The gateway status is regional, while the supplied traces and logs are only a subset.
